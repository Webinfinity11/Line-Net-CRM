# გუნდის ნაკადის QA — 2026-09-24

შემოწმებულია `08-team-flow-plan.md`-ით განსაზღვრული ნაკადი: მენეჯერი → მოთხოვნა/დანიშვნა → ინდივიდუალური სამუშაო და ჩაბარება → საერთო დასრულება → შემოწმება/დახურვა → ფინანსური დოკუმენტები და მეილის გადახედვა.

## რა გასწორდა QA-ის დროს

1. **ხელახლა გახსნა:** დასრულებული/დახურული შეკვეთის აქტიურ სტატუსში დაბრუნება ასუფთავებს წინა ჩაბარებებს, დასრულების თარიღებს, შენიშვნასა და გარანტიას. შემსრულებელს სამუშაოს თავიდან დაწყება და ჩაბარება შეუძლია.
2. **გუნდის მუშაობა:** მეორე შემსრულებლის „დაწყება“ დამოკიდებულია მის საკუთარ ღია ვიზიტზე. პირველი კოლეგის დაწყება მას ღილაკს აღარ უკარგავს. თანამშრომლის სრული დასრულება ხურავს ყველა ღია ვიზიტს; გარანტია იწყება საერთო დასრულებისას.
3. **თანხის თანმიმდევრულობა:** ბოლო სერვისის წაშლისას ძველი ჯამი აღარ რჩება. პოზიციებიან შეკვეთაზე ფორმა პოზიციების ჯამს ვეღარ გადაწერს. პოზიციების გარეშე ხელით მითითებული თანხა შენარჩუნებულია.
4. **დღგ:** პოზიციების გარეშე ხელით მითითებულ თანხას ინვოისში, აქტსა და მეილის შიგთავსში შესაბამისი დღგ გამოეყოფა.
5. **დანიშვნის უფლებები:** შეკვეთის შექმნის, რედაქტირების, პირდაპირი და გეგმის ერთეული/ჯგუფური დანიშვნისას მოწმდება მომხმარებელი. კლიენტის ანგარიში, დაბლოკილი ან არარსებული მომხმარებელი შემსრულებლად ვერ ინიშნება.
6. **მოთხოვნების ციკლი:** პირდაპირი დანიშვნა შესაბამის მოლოდინში მყოფ მოთხოვნასაც აგვარებს. გაუქმებულ/დახურულ შეკვეთაზე დარჩენილი მოთხოვნის უარყოფა შესაძლებელია, დამტკიცება — არა. უკვე გაგზავნილი მოთხოვნა ინტერფეისში ჩანს.
7. **გადახდების კონკურენცია:** ერთდროული გადახდების ჯამის განახლებას შეკვეთის რიგის ბლოკირება იცავს; დამატებულია ერთდროული მოქმედებების ტესტი.
8. **წვდომა:** საჯარო თვითრეგისტრაცია ელფოსტითა და Microsoft-ით გამორთულია, რათა უცხო პირმა ნაგულისხმევი შემსრულებლის როლი და შეკვეთების დაფაზე წვდომა ვერ მიიღოს. ანგარიშების ადმინისტრატორის მიერ შექმნა რჩება.
9. **კონტაქტები:** „მეილს იღებს“ მონიშვნა ელფოსტის გარეშე აღარ ინახება.
10. **ფილტრი:** პასუხისმგებელი მენეჯერის ფილტრი სხვა საძიებო პარამეტრებს ინარჩუნებს; ფორმა გვერდის სათაურის ვიწრო კონტეინერიდან გამოყოფილია.

ჩვეულებრივი `npm test` ინტეგრაციის 26 ტესტს გამოტოვებს განზრახ: ისინი ცალკე ბრძანებით, იზოლირებულ ბაზაზე წარმატებით შესრულდა. `scripts/qa-integration.mjs` ქმნის დროებით PostgreSQL კლასტერს, იყენებს მიგრაციებს და ბოლოს ასუფთავებს მხოლოდ საკუთარ გარემოს. საჭიროა ლოკალურად დაყენებული `initdb` და `pg_ctl`.

ინტეგრაციაში რეალური actions და SQL ამოწმებს დანიშვნებს, მოთხოვნებს, მენეჯერის აღებას, გუნდურ ჩაბარებას, ხელახლა გახსნას, ვიზიტებს, სერვისების უფლებებსა და ჯამებს, გადახდებსა და კონტაქტებს. სესია იმიტირებულია როლების გადასართავად; რეალური მეილი არ იგზავნება.

`scripts/qa-http.mjs` რეალური შესვლით ამოწმებს ადმინისტრატორის, მენეჯერის, შემსრულებლისა და კლიენტის გვერდებს. შემოწმებულია სხვის შეკვეთასა და ადმინისტრატორის პარამეტრებზე წვდომის აკრძალვა, შემსრულებლის პასუხებში გადახდებისა და თვითღირებულების არყოფნა, კლიენტების მონაცემების გამიჯვნა, ინვოისი, მეილის გადახედვა და საჯარო რეგისტრაციის აკრძალვა. სკრიპტი მოითხოვს ცალკე გაშვებულ ლოკალურ სერვერს 3003 პორტზე და მხოლოდ `127.0.0.1`-ის `linenet_qa` ბაზას.

## ფარგლები და დარჩენილი შემოწმება

- **ვიზუალური და ბრაუზერში დაწკაპუნებით სრული QA არ დასრულებულა.** ბრაუზერის ინსტრუმენტი მიუწვდომელია (`Sky Computer Use native pipe startup failed`). HTTP-ით გვერდის გამართული რენდერი არ ადასტურებს 390px განლაგებას, ჰორიზონტალური სქროლის არქონას ან სკრინშოტზე ნაჩვენები sidebar-ის ვიზუალურ სისწორეს.
- რეალური Graph/SMTP მიწოდება არ შემოწმებულა მომხმარებლის აკრძალვის შესაბამისად; გაგზავნის ლოგიკა და შეცდომების დამუშავება დაფარულია იმიტირებული ტესტებით.
- ინვოისის საბოლოო ვიზუალური მორგება მომხმარებლის ნიმუშს ელოდება.
- QA-ისას საერთო პროდაქშენ ბაზაში სატესტო მონაცემები არ ჩაწერილა და არსებული მონაცემები არ შეცვლილა. ყველა მოქმედებითი ტესტი ცალკე ლოკალურ ბაზაზე შესრულდა.
- კლიენტს მეილი არ გაგზავნია. commit, push და deploy არ შესრულებულა.

ეს ანგარიში ავსებს `08-team-flow-report.md`-ს; ზემოთ მოცემული რიცხვები არის საბოლოო QA-ის შედეგები.


## დამატებითი QA — კლიენტის მეილის ყველა ძირითადი გზა

მომხმარებლის შენიშვნის შემდეგ დაემატა 38 ერთეული და 4 ინტეგრაციული ტესტი. ჯამური მიმდინარე შედეგებია ზემოთ; HTTP-ის 26 შემოწმება წინა QA-ს ეკუთვნის და ამ დამატების შემდეგ ხელახლა არ გაშვებულა.

**აღმოჩენილი და გასწორებული:** შემოსული წერილის იმპორტი `emailFrom`-ში ინახავდა `სახელი <ელფოსტა>`-ს, მაგრამ მიმღების ამრჩევი ამ ფორმატს უარყოფდა. ახლა იღებს ერთ გამგზავნს როგორც სუფთა მისამართიდან, ისე ამ ფორმატიდან; რამდენიმე მისამართს და CR/LF ჩასმას უარყოფს. კონტაქტების დუბლიკატები ასოების რეგისტრისა და გარე გამოტოვებების მიუხედავად ერთიანდება. ასევე webhook-ის საიდუმლოს შედარება ბაიტების სიგრძით ხდება, რათა არასწორმა მრავალბაიტიანმა მნიშვნელობამ გამონაკლისი არ გამოიწვიოს.

Graph/SMTP ტესტები იმიტირებულ მიმღებ არხებს იყენებს. რეალურ საფოსტო ყუთში მიწოდება, იქ მიმოწერის ვიზუალური დაჯგუფება და ელფოსტის კლიენტებში HTML-ის ვიზუალური რენდერი არ შემოწმებულა. რეალური კლიენტისთვის არაფერი გაგზავნილა; საერთო ბაზის მონაცემები არ შეცვლილა.

## ნავიგაციისა და ბეჭდვის დამატებითი შემოწმება

ბრაუზერთან დაკავშირება კვლავ ვერ მოხერხდა: კომპიუტერის ინსტრუმენტმა დააბრუნა `Sky Computer Use native pipe startup failed`; Chrome და ჩაშენებული ბრაუზერი მიუწვდომელია. ამიტომ ქვემოთ ჩამოთვლილი არის კოდში აღმოჩენილი პრობლემების შესწორება და არა დასრულებული ვიზუალური QA.

- შემსრულებლის desktop მენიუს დაემატა „ყველა შეკვეთა“; მანამდე ეს მიმართულება ძირითად ნავიგაციაში მხოლოდ მობილურზე იყო.
- მობილურის გასაშლელ მენიუში ღია ფონსა და sidebar-ის ღია ტექსტს შორის შეუსაბამობა გასწორდა მუქი ფონით. მოკლე ეკრანებზე დაემატა ვერტიკალური სქროლი.
- პროფილის ღილაკს დაემატა ხელმისაწვდომი დასახელება; ზედა ზოლში გრძელი სახელი შეზღუდულ სიგანეზე იკვეცება.
- ინვოისს დაემატა თეთრი ფონი, გრძელი სიტყვების გადატანა, ბეჭდვისას ცხრილის სათაურის გამეორებისა და სტრიქონების/ჯამების გაუყოფლობის წესები.
- აქტის ზედა ნაწილი მცირე ეკრანზე გადადის ახალ ხაზზე, მხარეების მონაცემები ერთ სვეტად ლაგდება; ბეჭდვისას ორი სვეტი რჩება.
- `npm run typecheck`, `npm test` (164 წარმატებული) და `npm run build` წარმატებულია. ინტეგრაციის 26 ტესტის ბოლო წარმატებული შედეგი წინა ეტაპიდანაა; ამ UI ცვლილებისთვის თავიდან არ გაშვებულა.

სკრინშოტზე sidebar-ის კონკრეტული ხარვეზის დასაზუსტებლად მომხმარებელს გაეგზავნა კითხვა. მისი ვიზუალური სისწორე, 390px-ზე სქროლი, ბრაუზერში სრული სამუშაო ნაკადი და PDF-ის გვერდები კვლავ დასადასტურებელია. საერთო ბაზა და რეალური ფოსტა ამ შემოწმებას არ გამოუყენებია.

ლოკალური URL-ის შემოწმებამ დამატებით გამოავლინა პორტის დამთხვევა: სხვა პროექტი IPv6-ით უსმენს `3002`-ს, ხოლო CRM — `127.0.0.1:3002`-ს. `localhost` ზოგჯერ სხვა პროექტის 404-ს აბრუნებდა. CRM-ის development სერვერი ხელახლა გაეშვა `BETTER_AUTH_URL` და `NEXT_PUBLIC_APP_URL` მნიშვნელობებით `http://127.0.0.1:3002`; `/login` აბრუნებს 200-ს. სხვა პროექტის პროცესი უცვლელი დარჩა. ლოკალური შემოწმებისთვის გამოიყენეთ მხოლოდ `http://127.0.0.1:3002`.
