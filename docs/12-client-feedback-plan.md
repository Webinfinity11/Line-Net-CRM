# კლიენტის შენიშვნები — გეგმა (2026-09-28)

წყარო: კლიენტის 17-პუნქტიანი სია. 1 (ავტომატური განახლება, `/api/sync` + `components/app/live-order-sync.tsx`) და 2 (სერვისების Excel კატეგორიებით, `lib/service-groups.ts`) უკვე გაკეთებულია ლოკალურად. დანარჩენი სრულდება ეტაპებად, ამ რიგით. ყოველი ეტაპი მთავრდება: typecheck + npm test, ლოკალური build, Chrome-ში შემოწმება 390/1440 ყველა შესაბამისი როლით, [QA] ჩანაწერების წაშლა. ატვირთვა — ბოლოს, ყველა ეტაპის შემდეგ.

კლიენტის ახალი მოთხოვნები ზოგან ცვლის ადრინდელ შეთანხმებას — ახალი მოთხოვნა მოქმედებს, ძველი წესი `CLAUDE.md`-ში შესაბამისად შეიცვლება:

- #8 ცვლის „კატალოგი ზუსტად ორ დონეა, ქვეკატეგორიის გარეშე“.
- #13 ცვლის „ავიღებ ქმნის მოთხოვნას, მენეჯერი ადასტურებს“ (docs/08, 2.1–2.2).
- #14/#17 ცვლის „ნაგულისხმევი დალაგება: სასწრაფო → … → დაბალი“; სასწრაფო თავის წითელ ნიშანს ინარჩუნებს.

## ეტაპი 1 — ფინანსები და ერთეულები (#7, #3)
- **#7** შემსრულებელი ვერ ხედავს ფასს, თანხას, ჯამს, ღირებულებას არსად: `/my`, `/my/board`, შეკვეთის გვერდი, სერვისების ბლოკი, ჩაბარების ფანჯარა, შეტყობინებები, API პასუხები. სერვერზე ჭრა (`getOrderForUser`, `listMyOrders`, `/my/board` query, `/api/orders/[id]/comments` არ ეხება). შემსრულებელი სერვისს კატალოგიდან ამატებს ფასის ნახვის გარეშე (ფასი კატალოგიდან ავტომატურად), ხელით ჩაწერილ პოზიციას ფასის გარეშე (მენეჯერი ავსებს). ტესტი: შემსრულებლის მონაცემებში ფასის ველი არ არსებობს.
- **#3** პოზიციის ერთეული — ჩამოსაშლელი სია (ცალი, მეტრი, კომპლექტი, წერტილი, საათი, მ², კგ, „სხვა…“ ხელით) ყველგან, სადაც პოზიცია ემატება (შეკვეთის სერვისები, სერვისის ფორმა, მასალები); `lib/units.ts`. ინვოისში, აქტში და Excel-ში რაოდენობის გვერდით ერთეულის სვეტი.

## ეტაპი 2 — შემსრულებლის ნაკადი (#13, #15, #4, #14, #17, #16)
- **#13** „ავიღებ“ მყისიერად ნიშნავს შემსრულებელს (მოთხოვნის გარეშე), შეკვეთა მაშინვე მის „დასაწყებში“ ჩნდება; მენეჯერს შეტყობინება „X-მა აიღო LN-…“ და ისტორიაში „აიღო: X · დრო“. მოთხოვნების ბლოკი/დადასტურება აღარ ჩანს (ცხრილი და ძველი ჩანაწერები რჩება).
- **#4** „კოლეგის დამატება“ შემსრულებლისთვის ბოლომდე მუშაობს: სიიდან კოლეგის არჩევა → მყისიერად ემატება (იგივე წესით, რაც #13), კოლეგას და მენეჯერს შეტყობინება. თუ რამე მიზეზით ვერ დაემატება (დაბლოკილი, უკვე დანიშნული), ღილაკი ან ოფცია არ ჩანს.
- **#15** ყოველ ასეთ მოქმედებაზე: ღილაკი pending მდგომარეობით, წარმატებაზე მწვანე შეტყობინება („დავალება აიღეთ“) და შეკვეთა ვიზუალურად გადადის შესაბამის სიაში/ჩანართზე; შეცდომაზე წითელი ტექსტი.
- **#14/#17** ნაგულისხმევი დალაგება ყველა სიაში (`/orders`, `/my` ჩანართები, `/my/board`, `/inbox`, `/portal`): ახლიდან ძველისკენ (created_at desc). ხელით არჩეული დალაგება რჩება.
- **#16** ქვედა ზოლის/გვერდის რაოდენობები და სიები ერთი და იმავე წყაროდან და ერთად ახლდება (`executorCounts` layout-ში და `/my` სიები; სინქრონი `live-order-sync`-ით). ტესტი: დათვლა და სია ერთსა და იმავე ფუნქციას იყენებს.

## ეტაპი 3 — კლიენტის კაბინეტი (#11, #12)
- **#11** `/portal`: ჩანართები სტატუსებით რაოდენობებით — ყველა, გაგზავნილი, მიღებული/დაგეგმილი, პროცესში, შესრულებული, გაუქმებული (`PORTAL_STATUS_LABELS`-ის ლოგიკით); ძებნა (ნომერი, სათაური, მისამართი) და ობიექტის ფილტრი. URL-ში (`?tab=&q=&site=`).
- **#12** ახალი გვერდი `/portal/orders/[id]` (მხოლოდ კლიენტის კომპანიის შეკვეთა, სხვა → 404): სტატუსი და ეტაპების რიგი, აღწერა, თარიღები (გაგზავნა, ვიზიტი, შესრულება), შესრულებული სამუშაოები (პოზიციების სახელები და რაოდენობა, **თანხის გარეშე**), ტექნიკოსის ჩაბარების შენიშვნა, მკაფიოდ გამოყოფილი „ფოტოანგარიში“ (სურათები `/api/files/[id]`-ით; ფაილის წვდომა კლიენტისთვის მხოლოდ საკუთარი კომპანიის შეკვეთის სურათებზე). ბარათზე მკაფიო ღილაკი „დეტალურად“.

## ეტაპი 4 — შეტყობინებები და სტატუსი (#6, #9, #10)
- **#6** ნებისმიერ გვერდზე ახალ დანიშვნაზე (type `assigned` და #13/#4-ის შეტყობინებები) ეკრანზე თვალსაჩინო ფანჯარა „ახალი დავალება · LN-… · ობიექტი“ ღილაკით „გახსნა“ → შეკვეთა; რამდენიმე ერთად — სია. იგივე წყაროდან, რაც ზარი (`/api/notifications`), სინქრონით. ხმა არა; ბრაუზერის შეტყობინება ნებართვის შემთხვევაში (არსებული).
- **#9** ჩაბარებისას (ტექნიკოსის ნაწილი და სრული `done`) შეტყობინება: შეკვეთის მენეჯერი (ან ყველა staff), ყველა ადმინი, და კლიენტის ლოგინები (კლიენტს — სრული დასრულებისას, ბმული `/portal/orders/[id]`). ტექსტში ნომერი, ობიექტი, შემსრულებელი. დაჭერით გადადის დავალებაში. კლიენტს მეილი არ ეგზავნება (client mail გამორთულია).
- **#10** მენეჯერის/ადმინის დადასტურებისას (`done → closed`) სტატუსი ყველასთან ერთდროულად იცვლება: კლიენტთან „შესრულებულია“. გამოიკვლიე, რატომ რჩებოდა „დაგეგმილია“ (portal-ის სტატუსის map, revalidatePath `/portal`-ზე, sync revision კლიენტისთვის) და გაასწორე; კლიენტს შეტყობინება „LN-… დასრულდა“.

## ეტაპი 5 — ნომენკლატურა (#8)
- ჯგუფი → ქვეჯგუფი → ნომენკლატურა. ჯგუფი = არსებული კატეგორია (`systems`), ქვეჯგუფი = ახალი ცხრილი (`service_subgroups`: id, system_slug, name, sort, active), `services.subgroup_id` nullable. მიგრაცია მხოლოდ ამატებს (CLAUDE.md-ის წესით). ქვეჯგუფი არასავალდებულოა — არსებული სერვისები ჯგუფში რჩება „ქვეჯგუფის გარეშე“.
- `/settings/services`: ზედა საერთო ძებნა, რომელიც მყისიერად (client-side) ფილტრავს ჯგუფს, ქვეჯგუფს და პოზიციას ნაწილობრივ დამთხვევაზე („HDMI“ → ყველა დაკავშირებული); ჯგუფის/ქვეჯგუფის შექმნა/რედაქტირება/წაშლა (ცარიელის), პოზიციის დამატება ქვეჯგუფში. შეკვეთის სერვისის ამრჩევი და Excel ექსპორტი ქვეჯგუფებსაც აჩვენებს.
