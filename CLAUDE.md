# Line Net CRM

Order-dispatch CRM for შპს ლაინნეტი (electrical / low-current contractor, Tbilisi). Georgian UI only.
Spec: `docs/02-mvp-spec.md` (MVP) + `docs/04-phase-1.5-spec.md` (agreed additions, all implemented except Microsoft integration which waits on Azure credentials). Do not add features beyond these unasked.

## Commands
- `npm run dev` (http://localhost:3000), `npm run typecheck`, `npm run build`
- `npm run test:integration` creates an isolated local PostgreSQL cluster, applies migrations, tests real actions, and removes the cluster. Requires PostgreSQL binaries on PATH; never loads `.env.local`. `scripts/qa-http.mjs` checks role-specific server-rendered pages against an explicitly isolated QA server on :3003; it is not a visual browser test.
- `npm run db:demo` fills a year of demo history (clients marked `[demo]`); `npm run db:demo -- clear` removes exactly those rows before handover.
- Schema changes: edit `db/schema.ts`, write the SQL by hand as the next `db/migrations/00NN_<slug>.sql` and append a matching entry to `db/migrations/meta/_journal.json` (drizzle snapshots stop at 0005, so `drizzle-kit generate` prompts about old diffs and fails without a TTY), then `npm run db:migrate`. `.env.local` points at the Neon database. `db:push` is only for throwaway local databases; `npm run db:seed` creates demo users (admin1234 / meneger1234 / user1234), checklist templates and demo orders; safe to re-run
- Env lives in `.env.local` (see `.env.example`)

## Architecture
- Next.js 16 App Router. Route params and searchParams are Promises; use `PageProps<"/path">` and `await`.
- `proxy.ts` (not middleware) redirects unauthenticated requests to `/login` by cookie presence only; real auth checks happen in `lib/session.ts` (`requireUser(roles)`).
- Auth: Better Auth + drizzle adapter + admin plugin. Roles: `admin | manager | executor | client` stored on `user.role`; a `client` login also carries `user.client_id`. Microsoft SSO enabled only when `MICROSOFT_*` env set.
- Data: Drizzle ORM, schema in `db/schema.ts`. Anything importing `@/db` or `@/lib/orders` is server-only. Pure helpers shared with client components live in `lib/order-utils.ts`.
- Mutations are server actions in `actions/*.ts`; they return `ActionResult` (`{ok:true}` / `{ok:false,error}`) and call `revalidatePath`. Authorization is enforced inside every action.
- UI: Tailwind 4 + shadcn (base-nova style on `@base-ui/react`). Triggers use `render={<Button/>}` instead of `asChild`. Selects in forms use `NativeSelect`: a custom Base UI dropdown with native-compatible value/onChange and form submission, reset and required validation; lists over 12 options include search. Server pages pass plain `<option>`/`<optgroup>` children.
- All user-facing strings and status/priority/payment labels and colors are in `lib/i18n.ts`.

## Domain rules
- Order statuses: new → assigned → in_progress → done → closed, plus cancelled. Assigning executors to a `new` order sets `assigned`; removing all sets `new`.
- Executors see all active triaged orders on `/my/board` (safe fields only); details, comments and files remain limited to their assignments. They see billable lines (name, quantity, unit) but never prices, amounts, totals, payments or material costs: `getOrderForUser` nulls `amount` and every `unitPrice`, `listMyOrders` drops `amount`, `addOrderItem` takes an executor's price from the catalogue (manual line → 0) and `updateOrderItem` ignores a price sent by an executor; `OrderServices` gets `financeVisible={staff}`. An executor takes an order instantly with „ავიღებ“ on `/my/board` (`takeOrder` in `actions/requests.ts`: history `self_assigned` „აიღო“, the order's manager or all staff get a `taken` notification) and adds a colleague from the order page (`addColleague`, candidates = active executors not yet assigned); every such button is one click with a pending state, a green toast and `router.refresh()`. The old request/approval flow (`order_requests`, `requestAssignment`/`decideRequest`) stays in the database and the actions but is no longer shown anywhere.
- Orders created from email have `source='email'`, `triaged=false` and appear in `/inbox` until a manager saves them via the edit form (sets `triaged=true`) or cancels them.
- Cron endpoints (`/api/cron/schedules` daily, `/api/cron/poll-mail` every 10 min, both listed in `vercel.json`) accept `CRON_SECRET` or `INBOUND_EMAIL_SECRET` through `lib/cron-auth.ts`. Vercel's scheduler only ever sends `CRON_SECRET`, so checking one of them silently 401s the run.
- Inbound mail: `POST /api/inbound-email` (Bearer `INBOUND_EMAIL_SECRET`) or Graph polling `GET /api/cron/poll-mail`; both call `lib/inbound-email.ts` which dedupes on `email_message_id`.
- Attachments are stored on disk under `UPLOAD_DIR`, or in Vercel Blob when `BLOB_READ_WRITE_TOKEN` is set (`lib/storage.ts`, production), and served through `/api/files/[id]` after an auth check (staff, assigned executors, and a client for `image/*` files of its own company's orders). A local server without the Blob token cannot read production uploads (500); test file access with files uploaded locally.
- Maintenance schedules (`service_schedules`) generate orders via `lib/schedules.ts` (idempotent per schedule + due date); triggered by `instrumentation.ts` daily, `/api/cron/schedules`, or the "გენერაცია ახლა" button.
- Categories (formerly "systems"; the customer does not want the word or the menu item): rows in the `systems` table (slug primary key). Orders, services, schedules and equipment store the slug in `system_type`; `SystemType` is a plain string. Every UI label says "კატეგორია". Admins manage them at `/settings/services/categories` (button on the services page; `/settings/systems` redirects there). Server code reads `lib/systems.ts` (`systemLabels()`), client components read `SystemsProvider` hooks; never list categories from the static `SYSTEM_ORDER`/`SYSTEM_LABELS`, which only seed a fresh database. Actions validate a submitted slug with `systemSlug` from `lib/systems.ts`, an async refine, so they parse with `safeParseAsync`. Services are grouped by category on the services page and in the order's service picker.
- Services: `services` is the price catalogue (admin screen at `/settings/services`); `order_items` are the billable lines on an order and drive `orders.amount` through `lib/order-items.ts`. Lines keep their own name/unit/price, so editing the catalogue never rewrites past orders; a line can also be typed by hand ("✎ ჩაწერა ხელით", no `service_id`). Deleting the last billable line clears the computed total; editing the order cannot override an existing line-driven total. Assigned executors receive billable lines (without prices) and may add lines or edit/remove only their own lines while assigned/in_progress. A line's unit is edited inline like its quantity (`updateOrderItem(itemId, quantity, unitPrice?, unit?)`; `UnitInput` in the row saves on blur), by staff on any line and by an executor on their own. On the catalogue and category screens a row opens its editor and the rest (disable, delete, reorder) sits in one "⋯" menu; active is the default state, only "გამორთული" is labelled. The catalogue has three levels, category → optional subgroup → service: `service_subgroups` (`system_slug`, `name`, `sort`, `active`) and nullable `services.subgroup_id` (migration 0012); subgroups are managed on the services page („+ ქვეჯგუფი“ is its own button on the category header, which has no ⋯ menu; rename from the name, its own ⋯ for order/disable/delete-when-empty; `actions/subgroups.ts`, `lib/subgroups.ts`), the service form has an optional „ქვეჯგუფი“ select filtered by category, services without one sit under „ქვეჯგუფის გარეშე“; the services page renders through `components/app/services-catalogue.tsx`, whose search filters instantly on the client across category, subgroup and service names and mirrors `?q=`/`?cat=` in the URL so the Excel link stays right; the order's service picker labels „ქვეჯგუფი — სერვისი“ and the services export has a „ქვეჯგუფი“ column. A service must have a category (`actions/services.ts`), each category group on the services page has its own "+ სერვისი" that opens the form with that category chosen, the categories screen counts services and orders separately (services link to `?cat=`) and renames through a dialog opened from the name (an always-editable name field got typed into as if it were "new" and silently renamed a category), every active category shows on the services page even while empty, the services search matches category names too, and creating a category lands on `/settings/services?cat=<slug>` so its first service is one click away, and the order's service picker lists the order's own category first. How an order arrived (tender, call, project) is the order type, never a category.
- Quotes (`/quotes`, `quotes` tables) are not used by the customer: removed from the menu and the dashboard, code and data kept. Do not link to them.
- Order form: in its finance block the manager only sets the amount. Deadline, duration, VAT and warranty are no longer on the form; `updateOrder` keeps a field that the form did not send, and a deadline that only mirrored the visit day follows the visit.
- Client portal: a `client` login sees `/portal` (its company's orders, portal status wording from `PORTAL_STATUS_LABELS`, no money, no people) and `/portal/new`. `createPortalOrder` creates `source='portal'`, `triaged=false` orders that land in `/inbox` and notify staff. Every staff page redirects a client home, and home sends it to `/portal`. Public email/password and Microsoft auto-registration are disabled: users must be provisioned by admins. Admins create client logins on the users screen (role "კლიენტი" + company) or on the client card ("კლიენტის კაბინეტი"). Client components check staff with `isStaffRole` from `components/app/nav.ts`; `role !== "executor"` is not a staff check. `/portal/sites` lets a client add and edit its own company's sites (no delete); `createPortalSite`/`updatePortalSite` take the company from the session and scope both the lookup and the update by it, then notify staff without an order link. `/portal/new` reuses `PortalSiteDialog` and selects the site it just saved. Until a manager accepts a portal order (`triaged=false`) the client sees "გაგზავნილია", not the portal label; `updateOrder` turning a portal order's `triaged` false→true notifies the company's client logins once ("თქვენი შეკვეთა მიღებულია"). `/portal` has status tabs with counts (`lib/portal-tabs.ts`: ყველა / გაგზავნილი / მიღებული-დაგეგმილი / პროცესში / შესრულებული / გაუქმებული), a search (number, title, site), a site filter and a month select, all in `?tab=&q=&site=&month=` (`components/app/portal-filters.tsx`), newest first; `done` (handed over, awaiting the manager's check) sits in „პროცესში“ and „შესრულებული“ holds only `closed`; tab counts follow every filter. A client edits its own request while the order is `new`/`assigned` (`updatePortalOrder` in `actions/portal.ts`: company from the session, row locked, refused from `in_progress` on; only the `/portal/new` fields), every change is one `client_edited` event `{changes:[{field,from,to}]}` shown to staff in the order history (`clientEditedEventText` in `lib/i18n.ts`) and the manager (or all staff) gets a bell-only notification. `PortalSiteDialog` carries a Leaflet pick mode (`components/app/map-view.tsx`): the client drops or drags one pin, `lat/lng` travel as hidden fields and win over geocoding; without a pin the geocode behaviour stays. The client's six workflow steps (`WORKFLOW_STEPS` in `lib/workflow-view.ts`) call the `done` step „სამუშაო შესრულებულია, მიმდინარეობს შემოწმება“ (compact: „შემოწმება“). Every card opens `/portal/orders/[id]` (button „დეტალურად“ and the card itself): `getPortalOrder` in `lib/portal.ts` is scoped by the session's company (anything else → `notFound()`) and shows status + steps, description, dates, work items without prices, technicians' handover notes and a „ფოტოანგარიში“ of `image/*` attachments. Client notifications carry `orderId`; `/api/notifications` and the notifications page return a role-aware `href` (`lib/notification-link.ts`: clients → `/portal/orders/[id]`, others → `/orders/[id]`).
- Technician page `/my`: tabs ახალი / მიმდინარე / ჩაბარდა / დახურული (`?tab=`). The card's main button follows the status: "დაწყება" (`startVisit`, opens the visit and sets in_progress), then "სამუშაო შესრულებულია". On phones the tabs live in the bottom bar (counts from `executorCounts` in `app/(app)/layout.tsx`) and the in-page strip is hidden.
- Checklists: admins manage category templates at `/settings/checklists` (linked from services, no new menu item). New staff/scheduled orders and first categorization of untriaged portal/email orders receive the category default inside their creation/triage transaction. Existing open orders are never backfilled. Assigned executors and staff tick items; staff add/remove order items. A technician's handover requires a note of at least 5 characters, all required checklist items and their own photo (`image/*`); staff completing or closing an order only need the note (`completionProblems(..., staff)` in `lib/completion-gates.ts`). The legacy `requires_photo` flags no longer control this requirement.
- Notifications: `lib/notify.ts` `notifyUsers()` writes rows and emails via SMTP when configured. Hook points: assignment, executor marks done, inbound email, schedule generation, new comment (order manager or all staff when none, plus assignees, never the author or clients; recipients from `lib/comment-notify.ts`; bell only; one unread comment notification per person per order). `lib/reminders.ts` adds `visit_today` (once per Tbilisi day), `overdue` and `done_waiting` (once per recipient/order), with `overdue` only after a defined due date has passed; `done_waiting` only after its due date has passed, or after more than 3 days since completion when no due date exists. Reminders exclude clients and banned users, with `{ email: false }` (bell only). Daily at 08:00 Asia/Tbilisi via `/api/cron/reminders` and the internal scheduler (`INTERNAL_CRON=0` disables it); authenticated `?dry=1` previews recipients without writes. The bell polls `/api/notifications?since=<id>` every 10 seconds while visible (plus once when the tab becomes visible) and shows browser notifications after user permission; new `assigned`/`taken` items also open a fixed „ახალი დავალება“ card (`components/app/new-task-alert.tsx`, rendered by the bell on every page and role) with „გახსნა“ (marks read, follows `href`) and „დახურვა“. Handover: `completeOrder` notifies the order's manager (or all staff) plus every admin with type `done` on both a partial and a full handover (recipients and texts in `lib/completion-notify.ts`, never the actor), and the company's client logins on full done („LN-… ჩაბარდა“, `orderId` set); `setStatus` → closed notifies the client („LN-… შესრულებულია“; `PORTAL_STATUS_LABELS.closed` is „შესრულებულია“) and every status change and `setAssignees` revalidate `/portal`, so the client's list updates live through `live-order-sync`.
- Maps: `components/app/map-view.tsx` wraps Leaflet (client-only, dynamic import). Sites carry `lat/lng`; `lib/geocode.ts` uses Nominatim best-effort on site save.
- Excel: `/api/export?type=...` (SheetJS) and `actions/import.ts` for client import. Reports queries in `lib/reports.ts`.
- Times: all "today"/day boundaries use Asia/Tbilisi explicitly (`lib/schedule-utils.ts`).
- Contacts: a site carries its own `contact_name` / `contact_phone`; `orderContact()` in `lib/order-utils.ts` prefers it over the client-wide contact, and the order page, `/my`, the act and the quote PDF all go through it. A technician calls the branch, not the head office.
- VAT: `orders.vat_percent` mirrors `quotes.vat_percent` and is copied on conversion. `orders.amount` is gross (VAT included) because payments are matched against it; `recomputeOrderAmount` applies the rate to the net lines. A rate of 0 hides every VAT row.
- Finance: `order_payments` is the source of truth; `orders.paid_total`/`payment_status` are recomputed by `lib/payments.ts` inside the same transaction. Never set payment_status by hand. Executors get orders only through `getOrderForUser`/`listMyOrders`, which strip payment fields, material costs, `amount` and line prices on the server; only line names, quantities and units reach an executor.
- VAT: `orders.vat_percent` (default 0) mirrors `quotes.vat_percent` and is copied on conversion. `orders.amount` is the **gross** total — `recomputeOrderAmount` multiplies the line sum by the rate — so payments are matched against what the client owes. `vatBreakdown` in `lib/finance.ts` produces the net/VAT/gross rows for the order card and the handover act; a rate of 0 hides them.
- Contacts: a site carries its own `contact_name`/`contact_phone` for branch networks. `orderContact` in `lib/order-utils.ts` resolves who to call — the branch wins over the company contact — and is used by the order page, the technician list, the act and the quote PDF. Never read `client.phone` directly for a call button.
- Work flow: visits (`order_visits`, one open per executor+order) are separate from completion. `completeOrder` enforces the note, the executor's own photo and the required-checklist items inside its transaction for a technician's handover (the customer: nothing reaches the manager without photo and finished info); staff finishing or closing an order only need the note; each executor hands over only their part and closes their own visit. The order becomes done only after every assignee hands over, with named combined notes. Staff can complete the entire order. Reopening done or closed work resets all handovers and completion/warranty metadata; staff completion closes every open visit. `done` → staff `closed` (verified). Closed orders are frozen except for admins.
- Never export helpers from `actions/*.ts` ("use server" makes every export a public endpoint); put shared logic in `lib/*` with `server-only`.
- Tests: `npm test` (vitest, pure logic in `tests/`).

- Team flow: `docs/08-team-flow-plan.md` is implemented locally. `manager_id/manager_at` are claimed atomically only when empty; explicit takeover logs `manager_changed` and notifies the previous manager. Assignment requests (legacy) use a partial unique pending index; instant take/add-colleague go straight through `syncAssignees`, whose optional `eventType` writes `self_assigned` for a self-take.
- Default order lists (`/orders`, `/inbox`, `/my`, `/my/board`, `/portal`) sort newest first (`created_at desc`; `orderByFor` default is labelled „ახალი ზემოთ“); explicit sorting remains available and urgent keeps its red badge. `/orders` and `/portal` take `?month=YYYY-MM` (`lib/month-filter.ts`: `parseMonth` → Tbilisi month bounds on `created_at`, `monthOptions` from the oldest order to now with Georgian month names; the `/orders` chip keeps the other filters). The orders table has a „კლიენტი“ column (`data-col="client"`) and dashboard rows carry the company name. Every path to `done`/`closed` fills `orders.completed_at` once (kept on close, cleared on reopen) whether or not a due date exists; `/orders?status=done|closed` sort by `completed_at desc` and show „დასრულდა: <date>“; the dashboard counts and links `done` and `closed` separately („დახურული“ → `/orders?status=closed`). `live-order-sync` falls back to a 10 s poll when SSE is unavailable. `executorCounts` in `app/(app)/layout.tsx` and the `/my` lists both come from `listMyOrders` + `executorBucket`, so the bottom-bar counts always match the cards. `UnitInput` is a `NativeSelect` over `lib/units.ts` plus „სხვა…“ that reveals a required text input; the value travels in a hidden input with the caller's `name`, so forms keep using `FormData`.
- Executor competencies: `executor_competencies` (`user_id`, `system_slug`; migration 0013). No rows means „ყველა“ (every category), so existing executors lose nothing; rows restrict the executor to those categories. Admins set them on the user form (role executor: „ყველა კატეგორია“ or selected categories from `SystemsProvider`; `actions/users.ts`). `lib/competencies.ts` (`competenciesByUser`, `candidateExecutors`, `boardVisibility`) and the pure `lib/competency-utils.ts` (`canHandle`, `competenceLabel`) drive the candidate lists (order page, schedule, bulk assign: only executors who cover every selected category or have „ყველა“, already-assigned people stay listed, a short competence label next to the name) and `/my/board` plus its bottom-bar count (triaged active orders whose category the executor covers). The server never blocks an assignment on competence; only the lists are filtered. `/my` titles follow the tab („ყველა დავალება“, „დასაწყები დავალებები“, „მიმდინარე დავალებები“, „ჩაბარებული დავალებები“, „დახურული დავალებები“) and the board is „ყველა დავალება“.
- Staff review done orders and close them; `/orders/[id]/invoice` prints an editable-layout invoice. Admins fill company and bank details at `/settings/company`.
- Client mail: `client_emails_enabled` defaults false (missing setting means disabled). Only `lib/client-mail.ts` sends client messages; generic notifications never email client logins. Received follows initial triage, scheduled follows visit changes with assignees, completed requires explicit close checkbox. Graph Mail.Send is requested only with OUTLOOK_SEND=1, otherwise SMTP is used when configured. Attempts/skips are logged; preview never sends. CLIENT_MAIL_DRY_RUN=1 blocks all client transport calls during local validation. Never enable or send mail as part of development checks.
- Site contacts are separate from primary call contacts. Staff manage contacts; client sessions can create/edit only their own company's contacts. Opted-in site email contacts take precedence over company email; inbound requests reply to the original sender in-thread.

## UI rendering rules
- Date/time fields use `DateField`, `TimeField`, `DateTimeField` from `components/ui/date-field.tsx` (Georgian app calendar, typed time or 15-minute choices); keep hidden form values in ISO local format, with validation and form reset. Never use native date/time pickers.
- Motion must never be the reason something cannot be read. `Reveal`, `CountUp`, `DrawnArea`, `GrowBar` and `Ring` in `components/app/motion.tsx` start from the finished state and only rewind once the script confirms the element is below the fold; `ln-pop` never animates from full transparency. Everything yields to `prefers-reduced-motion`.
- Theme: `next-themes` through `components/app/theme-provider.tsx` in the root layout (`attribute="class"`, system default) with a სისტემის / ღია / მუქი radio group in the profile menu (`components/app/theme-menu.tsx`); the choice persists in `localStorage`. The provider forces `light` on the print routes (`/orders/[id]/act|invoice|sheet`, `/quotes/[id]/pdf`) without overwriting the saved choice, and `app/(print)/layout.tsx` sets `color-scheme: light`. The dark palette is the `:root.dark` block in `app/globals.css` (accent lightened to #5aa3ab for text contrast). Components use semantic tokens (`bg-background`, `bg-card`, `bg-muted`, `text-foreground`, `text-muted-foreground`, `border-border`, `text-primary`) or `dark:` pairs; a hard-coded light hex that has no dark counterpart is a bug.
- Per-person view preferences (`components/app/view-prefs.tsx`) hide blocks by `data-view` / `data-col` through a small stylesheet, so the screens stay server-rendered.
- The Tailwind scale is px-based (`--spacing: 4px`, px text sizes, px breakpoints in `app/globals.css`). Some embedded browser panels force a large root/minimum font size; px keeps spacing stable. Do not reintroduce rem-based tokens.
- Sorting names in anything rendered on the server and hydrated in the browser goes through `compareNames` in `lib/order-utils.ts`, never `localeCompare(…, "ka")`: Node's ICU and Chrome order Latin and Georgian names differently and React threw hydration error #418 on the order form.
- `formatDate` / `formatMoney` in `lib/i18n.ts` are deterministic (manual formatting, Tbilisi timezone). Never use `toLocaleString`/`Intl` currency formatting in components: Node and browsers produce different output and React reports hydration mismatches.
- Maps: `components/app/map-view.tsx` uses OpenStreetMap raster tiles (free, keyless), numbered `divIcon` pins with popups, `fadeAnimation: false` and a ResizeObserver-driven `invalidateSize`. CARTO tiles need an API key now; do not switch back. Optional Google Maps engine behind `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY`.
- Phone navigation (`components/app/mobile-nav.tsx`): staff get four destinations plus the hamburger sheet; an executor gets the four `/my` tabs plus the all-orders board; a client gets orders · a round "new" button · addresses. Only staff see the hamburger. The client's round button rises 22px above the bar, so client pages carry more bottom padding in the layout. Bar labels are Mkhedruli like the sidebar.
- PWA: `app/manifest.ts`, static icons in `public/` and `app/apple-icon.png`, `appleWebApp` + `themeColor` in the root layout. `public/sw.js` is a pass-through worker that caches nothing on purpose (data must always be fresh; no offline mode). `components/app/install-prompt.tsx` (root layout, rules in `lib/install-prompt.ts`) offers installation on phones only: Chrome's dialog on Android, a Share → „მთავარ ეკრანზე დამატება“ hint in iOS Safari only; after 8 s or on the second screen, never on login/print pages; "არა ახლა" snoozes 7 days (`localStorage` `ln-install`), the third refusal or an install ends it for good. `proxy.ts` lets `/manifest.webmanifest` and `/sw.js` through without a session.
- Dashboard rings (`components/app/dashboard/rings.tsx`): orders by status for the chosen period, and on-time completion (share of the period's completed orders closed by their deadline; orders without a deadline are listed apart). `DrawnArea` reveals its line with a growing clip, never a stroke dash: with `non-scaling-stroke` in a stretched viewBox the dash came out broken.
- Dashboard hero keeps its original layout (money received, change chip, comparison line, sparkline, "მოქმედება სჭირდება" aside) but every number follows the picked period through `lib/dashboard-period.ts` + `lib/dashboard-hero.ts`: received vs the comparison window (today → yesterday up to this hour, week → the 7 days before, month → last month to the same day, custom → the same number of days before), orders handed over with their total and unpaid balance (links to `/orders?payment=unpaid`), and the line bucketed by hour/day/week. ## Colour and type discipline
- The palette is written out at the top of `app/globals.css`: one value per role, four text levels, four surfaces. Before adding a colour, check whether one of those already means what you need — near-duplicates are what make a screen look assembled by several hands. Tailwind's own palettes (amber-*, rose-*, emerald-*) are not used in app code.
- The accent derives from the dark teal in `public/brand/logo.png` (#3c8189), darkened to #397b83 for text contrast.
- One accent (#397b83) for primary actions and active state. Status chips use the muted family in `STATUS_COLORS`. Red (#b13f32) only for problems (overdue, unpaid, urgent). Green (#25815a) only for money received or success. Everything else is neutral grey.
- Systems, order types and avatars in dense lists are neutral: a row must not carry more than two colours beyond its status chip. `SYSTEM_COLORS` is deliberately one neutral value for every system.
- Headings and buttons: FiraGO Bold (700), tight tracking, Georgian Mtavruli via `toMtavruli` (Button, CardTitle, DialogTitle, SheetTitle and dialog/menu triggers apply it automatically). Names, body text, table headers, form labels and aria/title attributes stay Mkhedruli.
- Cards are `.ln-card` (white, radius 20, soft shadow, no border) on a #f4f6fa page. Never nest a card in a card.
- Clickable things look clickable, and only those: text that opens something is `.ln-link` (accent #397b83, underline on hover/focus, pointer) or a button; a card or row that opens as a whole is `.ln-card-link` / `.ln-row-link` (hover #f6fafb, active, „›“ on the right, `padding-right` reserved). A row with its own buttons keeps the title as the only link. Whole-row links use the stretched-link pattern (`.ln-row-link-anchor` with `after:absolute after:inset-0` on the title, never an anchor inside an anchor), and secondary links inside the row (tel:, mailto:) get `relative z-10`. Phones and emails are always `tel:`/`mailto:` through `telHref`. Anything that does not open must not carry the accent colour or an underline. Rules live at the top of `app/globals.css`.
